# Applying a merge to the dotfiles host

After a merge to `main`, the merge is not finished until it is applied to the dotfiles host, or every difference left is covered by an active hold. The merger does this. If someone else merged (Ivan in the web UI, auto-merge), the first session to notice does it. The dotfiles host is the one machine chezmoi deploys to. A session that is not on it cannot apply; it comments on `nisavid/dotfiles#365` with the merge commit and asks the dotfiles orchestrator or a host session to apply it.

Authority: Ivan, 2026-10-18. It covers applying merged source to the host. It does not cover pushing, releasing, or any step beyond what the repository's own scripts already do.

## Terms

- **Difference**: a line of `chezmoi status` output. The ` R` lines of plain `run_`, `run_before_` and `run_after_` scripts are always shown, before and after an apply, so they are never a remaining difference; but they are still listed and matched against holds in step 2, because step 3 runs the uncovered ones. As of 2026-10-18 two are held, the skill-sync and Provingkit-sync scripts.
- **Hold**: a recorded exception to "apply everything". It names a target or a named group of targets, a release condition, and an owner or confirming owner.
- **Active hold**: a hold in the body of `nisavid/dotfiles#365`, in its "Active holds" section or its "Full apply owed" table. Read it with `gh issue view 365 --repo nisavid/dotfiles --json body -q .body`. The body alone is canonical; a hold that appears only in a comment is unconfirmed: treat its target as held and ask the dotfiles orchestrator to confirm it. Entries marked closed, resolved, released, or "not drift" are not active, and neither are the merge-admission windows that the same section records.
- **Who records or releases a hold**: Ivan, the Claude Foreman, the Codex foreman, the dotfiles orchestrator, or the target's owner, in that order of precedence (see the charter in `#365`). Anyone else asks the dotfiles orchestrator.
- **Escalate**: comment on `#365`, or message the dotfiles orchestrator session, with the exact state and what you need back before you can continue.

## Before merging

If the PR changes a target whose deployment needs separate approval (signing, installing software, replacing shared installs), ask for a hold on that target before merging, or say in the PR that none is needed.

## Procedure

1. **Sync the source.** The primary checkout `$HOME/.local/share/chezmoi` is chezmoi's source repository; chezmoi reads its `home/` subdirectory. Run `git fetch origin`. Then check, before merging anything: `git branch --show-current` is `main`, `git status --porcelain` is empty, and `git merge-base --is-ancestor HEAD origin/main` succeeds. If any check fails, do not switch the checkout, do not run `git merge`, and do not apply from it; escalate. One exception: if `git diff --quiet HEAD` succeeds (the working tree matches `HEAD`) and `git status --porcelain` shows no untracked `??` lines, the index is stale, and `git reset -q` clears it without touching files. After the reset, `git status --porcelain` must be empty before you go on; if it is not, escalate. Then run `git merge --ff-only origin/main`.
2. **List the differences.** Run `chezmoi status`. It prints paths relative to `$HOME`; prefix `$HOME/` for the absolute destination path. Sort every line, including the ` R` script lines, into covered by an active hold or not. A `DA` line under `~/.claude/skills` or `~/.agents/skills` is a skill that source still manages and the host has deleted; the retired-skills hold covers it. A newly merged skill is not `DA`, so it is never covered by that hold. If you cannot tell whether a line is covered, treat it as held and escalate. Also mark each uncovered line whose first column is not a space: the host changed that target since chezmoi last wrote it, which is a conflict (step 4). A line that starts with `D` is a target the host deleted, which chezmoi also treats as a conflict.
3. **Apply the uncovered ones, in order, by absolute path.** While any hold exists, never run a bare `chezmoi apply`, `chezmoi update` or `chezmoi init --apply`, because each also applies held targets. Pass file and script paths. A directory line (a new directory, or a mode change) is applied with `--recursive=false`, together with the uncovered files beneath it; without that flag, applying a directory applies all its children, held ones included. A new file needs its parent directory applied first. Targets passed together run in sorted path order, ignoring the before/after phases, so use separate invocations in this order:
   1. uncovered `run_before_` scripts, such as `save-acl.sh`;
   2. uncovered files, with any conflict resolved as step 4 says;
   3. uncovered `run_after_` and `run_onchange_after_` scripts, such as `restore-acl.sh`, and other always-run scripts.

   For each invocation, first run it with `chezmoi apply -n -v` and the same arguments, and check that it touches only uncovered targets. That output can contain decrypted private content, so run it as one command that captures the output and reads only its `diff` header lines: `out=$(chezmoi apply -n -v ARGS) && printf '%s\n' "$out" | grep '^diff '`. If the dry run fails, the `&&` skips the read and the command fails: stop and escalate. No header lines on a successful run means the invocation would change nothing. Run the capture and the read in the same shell invocation, because a variable does not survive between separate commands. Never print or quote the rest of the output, or the dry run's error text if it names private content, in a comment, a report or a transcript. A dry run cannot preview a conflicted target, since it fails with "could not open a new TTY"; leave conflicted targets out of the dry run. `chezmoi source-path $HOME/<target>` returns a script's source name, which shows its phase. A script's target path is its source path with the `run_`, `before_`, `after_`, `onchange_` and `once_` prefixes and the `.tmpl` suffix removed, in its target directory. `run_after_activate-zsh-gui-path.zsh.tmpl` becomes `$HOME/activate-zsh-gui-path.zsh`. Passing a source name fails with "not managed". Applying a `run_onchange_` or `run_once_` script this way records its state. If an apply or a script exits non-zero, stop at the first failure, do not continue to files or later scripts, keep its output out of comments and reports, and escalate with the exact state: the command, its exit code, and the paths involved. A failing `run_before_` guard such as `refuse-legacy-gitconfig.sh` exists to stop the whole apply.
4. **Conflicts.** `chezmoi apply` asks about a conflicted target on a terminal and fails without one. Settle each conflict from step 2 before the file phase (step 3.2), then apply it there. Decide which side is right. If source is right, apply that target with `--force`; for a host-deleted target, source is right unless the deletion was intentional. For the Claude Code URL-handler `.desktop` file, source is always right (see step 6). If the host is right, `--force` would overwrite it with older source: leave the target unapplied, capture the host version into a source PR, and escalate; apply only after that PR merges. If deciding is out of your scope, escalate and do not overwrite the host.
5. **Removals and configuration.** A target retired through `home/.chezmoiremove` shows in `chezmoi status` as ` D` and is removed by applying its path. A plain deletion of a source file shows nothing, and an apply does not prune it. For each merge commit `M` you are applying, run `git diff --no-renames --diff-filter=D --name-only M^ M -- home` and report each removed source path. Use the merge commit, not the checkout's earlier `HEAD`, because an earlier session may already have synced the checkout. A renamed source file counts as a removal of its old path. If any such merge commit changed `home/.chezmoi.toml.tmpl`, report that chezmoi's configuration needs regenerating.
6. **Verify and report.** Run `chezmoi status` again. The Claude Code URL-handler `.desktop` file is restored to the bare-name launch by every apply; that is by design (ADR 0002). Report every other remaining difference with the active hold that covers it. A remaining difference with no active hold means the merge is not finished: escalate it.
7. **Expired holds.** If this merge satisfies a hold's release condition, say so in the report and tell the hold's owner or the dotfiles orchestrator, who release it. Until they do, that target stays held.
