# Operate unattended Provingkit delivery

Use this procedure when preparing enrollment, stopping delivery, recovering an
interrupted delivery, or verifying the approved internal channel. The
[host contract](../../host/provingkit-delivery/README.md),
[disabled example](../../host/provingkit-delivery/config.example.json), and
[qualification cases](../../host/provingkit-delivery/qualification-cases.json)
define a static design. They provide no running service, setup executable,
credential-store integration, provider adapter, or qualified installation.

The existing [local installation procedure](provingkit-installations.md)
continues to own its selected artifact and native-registration route. Its
capabilities do not qualify cloud publishing or unattended account delivery.

## Bind the operation

Read this procedure from the reviewed source revision selected by the delivery
owner. Bind the approved channel, authenticated promotion record, immutable
artifacts, selected provider adapters, service configuration and dependencies.
An artifact checksum alone establishes neither an authorized publisher nor an
approved release. A field in candidate configuration cannot grant authority or
declare its own review clean.

Before live use, require independent review and clean Daybreak coverage of the
final revisions of every live-use component, qualification tool and relevant
dependency. Changed dependencies invalidate affected coverage. Planning review
and synthetic fixtures are not this security pass. Reuse valid unchanged
evidence rather than rerunning an unrelated review or demanding a new grant
for every covered operation.

Keep the service identity separate from ordinary agent sessions. Its code,
configuration and channel trust must be protected from both the service's
mutable inputs and ordinary agents. Establish actual privileges, not just
different account names or restrictive file modes. Do not put credentials in
source, CI, prompts, logs, command arguments, archives or delivery evidence.

Static source preparation may continue before a privileged installer is
accepted. At an actual privileged step, use `handling-privileged-steps` to
prepare the reviewed command, working directory, exact changes, handback
signal, verification and remaining gates. Preparation is not execution.

## Enroll once

The existing enrollment owner uses the approved private inventory to bind each
actual account, private audience, existing plugin entry and enabled choice.
This procedure supplies no account inventory or authentication material.
Preserve protected and unmanaged plugins, including RSL. Discovery of an entry
does not authorize managing it.

Use normal operator-controlled authentication for the one-time isolated
automation context. Do not copy one live refresh token into competing
independent holders, change default logins, weaken protections or bypass a
provider challenge. Select and qualify a supported credential store against
restart and refresh behavior. Ordinary releases must not require sign-in;
provider-required reauthentication is an exceptional recovery condition.

Before subscribing Claude accounts, verify preventive promotion controls and
whether ordinary agent credentials can bypass them. An audit after promotion
does not supply that boundary. Keep migration from uploaded content to a
subscription recoverable and verify actual content and enablement afterward.

For ChatGPT, use the selected qualified adapter and its account-bound readback.
Prefer its expected-release guard. If the approved unguarded route is selected,
enforce its accepted exclusive-writer arrangement, read before and after each
write, and stop on drift. That sequence is not atomic compare-and-swap.

## Deliver and verify

Release notifications and the catch-up timer invoke the same deterministic
work. A notification is a hint to inspect the authenticated channel, not an
instruction to run code or upload its payload. Verify the release before either
ChatGPT mutation or Claude repository promotion.

Under the exclusive run lock, read actual target state and bind channel,
artifact digest, account, entry and delivery version. Preserve enablement.
Persist write intent before mutation, then obtain fresh account-bound content,
version, audience and enablement readback. Verify changed and removed files.
An adapter's success exit, repository commit or shared cache is insufficient.

If a process stops after write intent, mark the outcome uncertain and reconcile
remote state before another attempt. If readback cannot decide whether the
write occurred, preserve the attempt and stop its dependent work. Do not
repeat it, delete an entry or infer rollback authority. Independent eligible
targets may continue where the shared safety boundary is unaffected.

Use the existing version issuer's approved delivery-version projection. Keep
versions immutable and increasing, including an approved higher prerelease
floor where necessary. Do not invent versions or delete and recreate an entry
to escape an installed floor. The real one-account canary may proceed before
all-account versioning is complete, within its own accepted contract.

The first useful milestone is a second unattended release on one account per
provider, with changed and removed content, preserved identity and enablement,
fresh readback and a useful fresh consumer. Expand only passing routes to the
four ChatGPT and three Claude scopes. One provider or shared cache cannot
establish all-account delivery. Record latency and actual operator prompts.
Longer credential-survival observations continue alongside useful operation;
silence and elapsed time alone prove no unattended behavior.

## Stop both mutation paths

Use the reviewed stop control to withdraw mutation permission for ChatGPT
writes and Claude promotion. Observe quiescence, in-flight intents and uncertain
outcomes; disabling a timer alone is insufficient. Content already on a
subscribed branch may still propagate. Record that residual state rather than
claiming local stop retracts delivered instructions.

## Recover forward

First reconcile the journal with actual provider state. Use retained known-good
content at a higher authorized delivery version when selected for recovery.
Verify content, identity and enabled state again. Do not mutate a known-good
artifact, overwrite unexplained state or reuse a consumed attempt.

Provider refusals and authentication challenges go through the existing
exception route. Notices contain only the actionable condition and nonsecret
identifiers, never credentials, codes, raw provider diagnostics or untrusted
commands. Preserve independent product, publication and deployment holds.

## Capture downstream use

Use `capturing-agent-procedures`. The accepted installer, host operator and
provider consumers load the reviewed procedure before their dependent work
and record the revision actually used. Retain naturally useful enrollment,
stop, recovery and verification results, not marker runs. Explicit file loading
and automatic discovery are separate observations.

Every release needs fresh account-bound installation/content evidence and a
model-free loading inventory where supported. Use a useful fresh consumer at
the milestone and when the loading contract changes. Subsequent ordinary work
supplies ongoing use evidence; do not start artificial model tasks for every
release or restart active user work to collect proof.
