Issue #216 · logic prototype

Minimal release operator surface

Disposable fixture only

Question this prototype answers

Can one compact command model keep the ordinary release path short while making authority, immutable inputs, cancellation, concurrency, partial effects, and recovery visible at every stage?

This page cannot sign or publish anything. It uses deterministic in-memory state, synthetic .invalid identifiers, and public fixture digests. It performs no network requests, persistence, cryptography, provider access, secret resolution, authenticator interaction, host inspection, or production verification. Command names and object shapes are prototype candidates, not compatibility promises.

Two compact designs, plus the working synthesis

DesignCommon pathAuthority and stateFailure behaviorVerdict
A · Explicit stage verbs
prepare, inspect, sign, publish		 Longer, but every step composes in automation. Each command names exact input and output objects. Cancellation and partial effects have an obvious owner. Safe and inspectable; too much object plumbing for routine use.
B · Guided release session
release run		 One memorable command and one guided review. Session state can obscure which bytes and authority moved. Resume, races, and ambiguous writes become session magic. Pleasant happy path; weak audit and recovery boundaries.
Working synthesis · Immutable intent + staged execution
release execute --intent …		 One guided view over the same explicit stages. A content-addressed intent binds profile, manifest, signer, expected head, and operation ID. The guide stops on cancellation, conflict, or possible effect and points to the exact inspect or reconcile command. Prototype this. No hidden session and no second semantics.

One package, independently enforceable surfaces

Secret-free core

profile, release prepare, inspect, status, object inspect, and evidence export resolve no secret and mutate no external system.

Operator-present mutations

sign, withdraw, reselect, rotate, and recover require an exact intent and a terminal prompt. The first local FIDO profile proves UV-gated unwrap, not exact-intent approval.

Independent verifier

release-verify has no credential, provider, authenticator, or network surface. Bootstrap and refresh are separate from pure current or historical verification.

Publication adapters

Adapters receive exact approved bytes and an expected prior head. They may replicate and read back; they cannot sign, change intent, choose authority, or fall through after an indeterminate write.

Private binding

A public profile names abstract secret slots. A separately selected binding maps them to opaque references. Serialized configuration, JSON results, logs, and evidence never contain resolved values.

Offline handoffs

Certifying identity, recovery media, and provider administration remain external ceremonies. The CLI prepares a digest-bound request and stops at handoff-required; it never imitates completion.

Discovery stays broad; authority stays narrow

      

        
Discovery
profile list, profile show, profile doctor, operation status, and object inspect are bounded reads with stable JSON.

        
Release writes
release prepare creates an immutable intent. sign, publish, withdraw, and reselect each consume one exact intent and expose their own receipt.

        
Lifecycle handoffs
signer rotate prepare, factor replace prepare, recovery operation prepare, and incident begin stop before separately controlled provider, root, factor, host, or media work.

        
Verifier
anchor init and trust refresh establish mutable local context. verify current and verify historical are pure evaluations over exact supplied bytes.

        
Configuration
Explicit --profile, --binding, and --environment beat discovery. Discovery checks one XDG location; runtime never merges ambient fragments or scans executable paths.

        
Read-only escape hatch
object inspect --address … exposes canonical objects and adapter receipts. No generic raw provider write belongs in the core CLI.

Operator-present prompts use the controlling terminal, never stdout. Noninteractive execution cannot infer consent. Stdout contains one versioned JSON envelope; stderr contains human diagnostics only. Signals before an effect map to cancellation. Loss of confirmation after a possible write maps to reconciliation required. The separate verifier retains its settled exits: 0 positive, 20 rejected, 21 indeterminate, 64 invalid request, and 70 internal failure.

      

    


    

      
What this can settle, and what it cannot

      
The model tests whether immutable intents, staged execution, typed handoffs, and an independent verifier make the full lifecycle understandable without hidden mutable context. It can drive later CLI/API requirements, fixtures, conformance cases, and executable documentation.

      
It does not select an implementation language, package layout, provider transport, credential mechanism, production path, repository name, compatibility term, or support promise. It is not a security control and must never be promoted into a production verifier, signer, publisher, or recovery tool.
